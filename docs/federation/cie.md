# CIE — OpenID Connect Federation profile (as implemented)

CIE ("Carta d'Identità Elettronica") login is implemented by the same broker code as SPID
(`services/federation-broker/internal/rp`), with a separate **`cie` profile**: its own RP entity, keys,
trust anchors, providers and ACR map. Read [`spid.md`](spid.md) first; this document lists only what
differs and what remains unverified.

> - The broker redirects the user to the **CIE OpenID Provider** chosen in configuration. It does **not**
>   implement any CIE card/NFC protocol; the authentication methods offered to the user (CIE app,
>   card reader, QR code, …) are whatever the configured CIE OP exposes.
> - All CIE tests run against the **LOCAL test federation** (`cmd/fedsim`, OP `cie-test`). They are not
>   conformance evidence. No real CIE OP and no Ministero dell'Interno pre-production environment has been
>   used.

## 1. Endpoints

Identical to SPID with `{profile} = cie`:

| Purpose | Path |
|---|---|
| RP Entity Configuration | `GET /rp/cie/.well-known/openid-federation` |
| Resolve endpoint | `GET /rp/cie/resolve` |
| OP callback (redirect URI) | `GET /rp/cie/callback` |
| Kratos facade | `/oidc/cie/…` (Kratos provider id `cie`, label "Entra con CIE") |

Kratos provider configuration: generated by `scripts/setup.sh` (local) or the `kratos.secrets.yml`
overlay (Kubernetes, see `infrastructure/helm/iam-platform/README.md`) with
`issuer_url: …/oidc/cie`.

## 2. Differences from SPID

| Aspect | SPID | CIE | Code |
|---|---|---|---|
| `iss` parameter in the authorization response (RFC 9207) | validated if present | **mandatory**; a response without `iss` fails with `invalid_response` | `rp/service.go` `HandleCallback` |
| IdP chooser | always shown | **skipped when exactly one CIE provider is enabled** (direct redirect to the OP) | `server/public.go` `authorize` |
| Chooser title | "Accedi con SPID" | "Entra con CIE" — "Seleziona l'ambiente CIE da utilizzare." | `server/templates/select.html` |
| Encrypted ID token | accepted if received as JWE | optional in the CIE profile (signed-then-encrypted); decrypted with `core-enc` keys when the token has 5 parts | `validateIDToken` |
| `core-enc` key type | API refuses non-RSA generation for SPID | EC keys allowed (`ECDH-ES`, `ECDH-ES+A128KW`, `ECDH-ES+A256KW` advertised/accepted) | `keys.Generate`, `keys.encAlg` |
| RP metadata `jwks` | `jwks` (or `signed_jwks_uri` in the docs) | `jwks` mandatory — the broker always publishes `jwks` | `EntityConfiguration` |
| CIE-only attributes | — | `email_verified`, `phone_number_verified`, `landline_number` are normalised by the broker but **not persisted** by identity-service (`KEEP_ATTRIBUTES`) | `NormalizeAttributes`, `services/identity-service/src/service.ts` |
| Upstream revocation | access token revoked right after UserInfo | same (CIE docs: revoke access token, not refresh token; no refresh token is requested) | `rp.Service.revoke` |
| Refresh tokens | not requested | not requested (CIE refresh rules, e.g. mandatory rotation and no ID token on refresh, are therefore not exercised) | `scopeString` |

Everything else — Entity Configuration, request object, PKCE S256, `private_key_jwt`, ID token and
encrypted UserInfo validation, `jti` replay protection, attribute normalisation, required attributes,
error codes and user messages, audit events, admin UI and admin API — is shared and described in
[`spid.md`](spid.md).

## 3. ACR mapping (UNVERIFIED for CIE)

The SPID/CIE OIDC docs v1.2.1 list the SPID ACR URIs for both SPID and CIE OPs, and no CIE-specific ACR
values were found during research ([`../architecture/research-notes.md`](../architecture/research-notes.md) §3).
The default CIE profile therefore uses:

| ACR (as configured) | Internal LoA |
|---|---|
| `https://www.spid.gov.it/SpidL1` | `urn:iam:loa:low` |
| `https://www.spid.gov.it/SpidL2` | `urn:iam:loa:substantial` |
| `https://www.spid.gov.it/SpidL3` | `urn:iam:loa:high` |

This mapping is **UNVERIFIED** and must be confirmed with the Ministero dell'Interno documentation and
onboarding team. It is editable per profile (**Profilo CIE → Mappa ACR → LoA interno**) without code
changes; the SPID map is never applied to CIE responses. Whether a CIE level is equivalent to the SPID
level with the same internal LoA is a policy decision ([`../security/assurance-levels.md`](../security/assurance-levels.md)).

## 5. Configuring CIE

Same screens as SPID ([`spid.md`](spid.md) §12), using **Profilo CIE** and selecting profile `cie` in
**Chiavi e certificati**, **Trust Anchor** and **Identity Provider**:

1. Profilo CIE: set environment, entity ID (e.g. `https://spid.example.it/rp/cie`), organisation data,
   redirect URI `https://<broker host>/rp/cie/callback`, authority hints, required attributes, ACR map.
2. Chiavi e certificati: make sure `cie/federation`, `cie/core-sig`, `cie/core-enc` have an active key
   (and certificates, if required by onboarding).
3. Trust Anchor: preview and pin the CIE Trust Anchor after out-of-band thumbprint verification
   ([`onboarding.md`](onboarding.md)).
4. Identity Provider: add the CIE OP entity ID. With a single enabled CIE provider the chooser is skipped.
5. Profilo CIE → Trust mark: paste the trust mark issued at onboarding.
6. Diagnostica: resolve the CIE OP (`openid_provider`) and our own RP (`openid_relying_party`).
7. Enable the profile. Note: the "Entra con CIE" button is rendered from the Kratos provider
   configuration and is shown even while the broker profile is disabled; clicking it then ends with
   "Questo metodo di accesso è momentaneamente disabilitato" (`profile_disabled`). To hide the button,
   remove the `cie` provider from the Kratos configuration.

Equivalent API calls: [`../operations/api-examples.md`](../operations/api-examples.md) (use `cie` in the
paths and bodies).
